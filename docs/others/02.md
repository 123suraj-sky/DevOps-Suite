# STAGE 2 — Azure Key Vault + Managed Identity

This stage improves your **security architecture**.

Currently you probably have something similar to:

```text
Docker Compose
      ↓
.env
      ↓
DATABASE_PASSWORD
JWT_SECRET
MAIL_PASSWORD
```

We want:

```text
                    Azure Key Vault
                   /      |       \
                  /       |        \
             DB_PASSWORD JWT_SECRET SMTP_PASSWORD
                  ↑
                  │
          Managed Identity
                  ↑
             Azure VM
                  ↑
             Application
```

Azure Key Vault is designed for securely storing secrets, keys, and certificates. Managed identities allow Azure resources to authenticate to supported services without you having to manage credentials in application code.

---

## 2.1 Inventory your secrets

Before creating anything, identify what your application actually needs.

For example:

```text
DATABASE_URL
DATABASE_USERNAME
DATABASE_PASSWORD
JWT_SECRET
MAIL_USERNAME
MAIL_PASSWORD
```

**Do not paste your actual secret values into documentation.**

---

## 2.2 Create Key Vault

Azure Portal:

**Key Vaults → Create**

Use something like:

```text
Name:
devopssuite-kv-<unique>
```

Choose the same region as your VM where appropriate.

Keep access policies/permissions restrictive.

---

## 2.3 Add secrets

For example:

```text
JWT-SECRET
DB-PASSWORD
MAIL-PASSWORD
```

Don't create secrets unnecessarily. Only move genuine sensitive values.

---

# 2.4 Enable Managed Identity on VM

Go to:

**VM → Identity**

Enable:

```text

```

Azure will associate an identity with your VM.

Conceptually:

```text
vm-devopssuite
       │
       └── Managed Identity
               │
               ▼
          Azure Key Vault
```

---

# 2.5 Give the VM permission to read secrets

Give the VM identity the minimum required Key Vault permission.

For your application, you generally want:

```text

  Get
```

Avoid giving broad administrative permissions.

This is the principle of:

> **Least privilege**

---

# 2.6 Test Key Vault access

SSH into your VM.

Use Azure CLI to verify that the VM identity can authenticate and retrieve an allowed secret.

For example, conceptually:

```bash

```

Then retrieve the secret using the appropriate Key Vault command.

**Do not put the returned secret into Git, logs, screenshots, or terminal recordings.**

```text
      ↓
```

Later, if you want a more advanced architecture, you can integrate the application directly with Key Vault.

For your current project, keeping the application architecture stable is more important.


```text

```

# 3.3 Modify GitHub Actions

Your pipeline becomes:

```text

   ↓
Backend tests
   ↓

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓

```

You can use GitHub's OIDC authentication to Azure rather than storing a long-lived Azure password/service-principal secret, which is the more modern approach.

---

# 3.4 Add ACR authentication

There are two parts.

### GitHub Actions → ACR

Configure GitHub Actions to authenticate securely to Azure/ACR.

### VM → ACR

Enable Managed Identity on the VM — which you already did in Stage 2.

Then grant the VM identity permission to pull images from ACR.

Conceptually:

```text
VM Managed Identity
       │
       ▼
Azure Container Registry
       │
       │ AcrPull
       ▼
Docker images
```

Azure documents this managed-identity pattern for ACR authentication.

---

# 3.5 Change Docker Compose

Instead of:

```yaml
services:
  backend:
    build:
      context: ./backend
```

you'll eventually have:

```yaml
services:

  frontend:
    image: devopssuiteregistry.azurecr.io/devops-suite-frontend:${IMAGE_TAG}
```

Now the VM doesn't need your entire source code repository to build the application.

It simply pulls a known image.

Your VM deployment becomes conceptually:

```bash
docker compose up -d
```


This is an important architectural improvement.

# 3.7 Add rollback


You can deploy:


That's a much better DevOps story than rebuilding source code on the VM.

# The order I'd actually follow

Don't try to implement all four at once.

| Phase       | Main goal                    | Difficulty |       Priority |
| ----------- | ---------------------------- | ---------: | -------------: |
| **Stage 1** | Azure Monitor + Alerts       |         ⭐⭐ |        **Now** |
| **Stage 2** | Key Vault + Managed Identity |        ⭐⭐⭐ |       **Next** |
| **Stage 3** | Azure Container Registry     |       ⭐⭐⭐⭐ | **After that** |
| **Stage 4** | Terraform                    |      ⭐⭐⭐⭐⭐ |       **Last** |

And there's a reason for that order:

**Monitor → Secure → Improve deployment → Automate infrastructure**

Each stage builds on the previous one.

### One important recommendation for your Azure credits

Since you're on Azure for Students and you've only spent around **₹158 so far**, don't create expensive resources just because Azure has them.

For this project, **VM + ACR + Key Vault + Monitor + Terraform** is already plenty.

You don't need AKS, Application Gateway, multiple VMs, Azure Kubernetes Service, or other large infrastructure just to make the project look impressive.

The real value is being able to explain **why you chose each service, how it works, how it integrates with your CI/CD pipeline, and how you would troubleshoot it.**

I would start with **Stage 1 (Azure Monitor)** and implement it completely before touching Key Vault.
